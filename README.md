# Meditron — многослойный скрининг анемии и дефицитных состояний

**Команда:** Мидия  
**Кейс:** Сеченовский университет  
**Версия:** 5.7.0  
**Тип решения:** врачебный Clinical Decision Support System (CDSS), а не автономная диагностическая система.

> **Машина структурирует данные. Врач видит человека.**
>
> Проект не автоматизирует эмпатию и не подменяет врача. Он забирает рутинное сопоставление лабораторных данных, показывает диагностическую неопределённость и помогает сделать результат понятным врачу и пациенту.

## 1. Цель и задачи

Цель — создать воспроизводимый врачебный прототип для двухуровневого скрининга анемии и латентных дефицитных состояний по лабораторной матрице из кейса.

Задачи:

- определить наличие анемии по порогам кейса;
- классифицировать профиль по **12 целевым классам**;
- независимо сопоставить ML и прозрачные клинические правила;
- не скрывать расхождения между гипотезами;
- показать, какой недостающий показатель лучше всего уменьшит текущую неопределённость;
- использовать жалобы, анамнез и препараты как отдельный клинический контекст, не подмешивая их в ML;
- сформировать понятный врачебный отчёт и отдельный лист для объяснения пациенту;
- работать без LLM; локальная Ollama является опциональным объясняющим и структурирующим слоем.

## 2. Что реализовано

- Streamlit-интерфейс для одного пациента;
- импорт текстовых PDF, TXT, CSV/TSV, JSON, XLSX/XLS и HTML;
- автоматическое распознавание ФИО, возраста, пола, клинического контекста и лабораторных значений там, где они присутствуют в документе;
- **опциональный локальный AI-parser** для сложных эпикризов: Ollama только структурирует жалобы, анамнез и препараты; ФИО перед передачей удаляется;
- ручная проверка и редактирование всех распознанных значений;
- автоматическая подстановка канонических единиц измерения при ручном вводе;
- 12-классовая Random Forest;
- независимый детерминированный clinical layer;
- uncertainty map и next-best measurement;
- причинно-следственные цепочки;
- поиск похожих лабораторных профилей;
- локальная обезличенная case-base подтверждённых врачом случаев;
- справочный МКБ-10;
- локальный RAG + Ollama для объяснения готового результата;
- брендированный PDF для врача и отдельная последняя страница для пациента;
- FastAPI;
- Dockerfile и docker-compose;
- автоматические тесты и отдельный воспроизводимый data audit.

## 3. 12 целевых классов

1. `no_anemia_no_deficiency`
2. `latent_deficiency`
3. `iron_deficiency_anemia`
4. `B12_deficiency_anemia`
5. `B12_deficiency_no_anemia`
6. `folate_deficiency_anemia`
7. `folate_deficiency_no_anemia`
8. `B6_deficiency`
9. `copper_deficiency`
10. `inflammation_anemia`
11. `mixed_deficiency`
12. `anemia_other`

## 4. Архитектура

Семь вычислительных слоёв:

```text
1. Нормализация и safety gate
          ↓
2. Клинические правила ←→ 3. ML (12 классов)
          ↓
4. Карта неопределённости
          ↓
5. Причинно-следственные связи
          ↓
6. Похожие лабораторные профили
          ↓
7. Опциональное AI/RAG-объяснение
          ↓
Врачебный интерфейс / PDF / режим разговора с пациентом
```

Карточка пациента, итоговое резюме, МКБ-10 и patient-facing представление не считаются отдельными диагностическими слоями.

Подробно: [`ARCHITECTURE.md`](ARCHITECTURE.md).

## 5. Данные и ML

Предоставленный датасет содержит **840 наблюдений и 48 переменных**, возраст 18–93 года и 12 целевых классов. ML использует 35 лабораторных показателей, возраст и пол — 37 признаков. Симптомов и анамнеза в обучающем наборе нет, поэтому они сознательно отделены от ML.

По воспроизводимому аудиту:

- Accuracy: `0.889`;
- Balanced accuracy: `0.878`;
- Macro-F1: `0.885`;
- ECE: `0.262`.

Random Forest имеет лучший Macro-F1 среди протестированных базовых моделей, но хуже откалиброван, чем LogisticRegression и GradientBoosting. Поэтому `predict_proba` в продукте называется **Model score**, а не вероятностью диагноза.

Полный аудит, таблицы, графики и скрипт воспроизведения находятся в [`research_audit/`](research_audit/) и [`DATA_AUDIT.md`](DATA_AUDIT.md).

Требуется установленный **Python 3.11+**.

Самый простой вариант:

```powershell

```

После запуска открыть:


Тесты:


## 9. Опциональная локальная Ollama

По умолчанию:

```text
OLLAMA_URL=http://127.0.0.1:11434
OLLAMA_MODEL=qwen2.5:7b
```

Пример:

```bash
ollama pull qwen2.5:7b
ollama serve
```

LLM используется только в двух опциональных задачах:

1. **структурирование клинического текста при импорте** — разделить уже написанное на жалобы, анамнез и препараты;
2. **AI/RAG-объяснение** уже рассчитанного результата.

LLM не меняет числа, `class_code`, Model score, клинические правила и не назначает лечение. Если Ollama недоступна, система автоматически использует обычный parser и детерминированное объяснение.

## 10. Входные данные

### Карточка

- ФИО — только для текущего интерфейса/PDF;
- возраст;
- пол;
- жалобы / симптомы;
- анамнез / хронические заболевания / значимые события;
- препараты.

### Лабораторные данные

Поддерживаются 35 показателей из спецификации кейса. Единицы нормализуются по `screening/schema.py`.

### Импорт

- текстовый PDF;
- TXT;
- CSV / TSV;
- XLSX / XLS;
- JSON;
- HTML-таблицы.

Сканированные PDF без текстового слоя в текущей версии не OCR-ятся автоматически.

**Один файл = один пациент.** Многопациентские таблицы отклоняются.

## 11. Выходные данные

- рабочий 12-классовый скрининговый класс;
- прозрачные clinical findings;
- независимый ML-ranking;
- карта неопределённости;
- следующий информативный показатель;
- причинные связи;
- сопутствующие сигналы;
- похожие reference-профили и локально подтверждённые обезличенные случаи;
- справочный МКБ-10;
- опциональное AI/RAG-объяснение;
- PDF для врача + отдельный лист для объяснения пациенту.

## 12. API

Основные endpoints:

- `GET /health`
- `GET /v1/schema`
- `POST /v1/predict`
- `POST /v1/import` — импорт одного пациента
- `GET /v1/sources`
- `GET /v1/model-info`
- `POST /v1/report`

`/v1/report` принимает `patient_name` отдельно от медицинского payload.

Опциональная защита API:

```text
HEALTHSCREENING_API_KEY=<secret>
```

## 13. Персональные данные и безопасность

Архитектурный принцип — **минимизация обработки ПДн**.

- ФИО не является ML-признаком;
- ФИО не входит в JSON результата;
- ФИО не сохраняется в локальную case-base;
- при AI-разборе текста ФИО и очевидные прямые идентификаторы удаляются до обращения к локальной Ollama;
- case-base хранит только обезличенные лабораторные признаки, возраст, пол и подтверждённую врачом метку;
- исходные импортированные поля всегда доступны для ручной проверки.

Сформированный PDF уже содержит персональные данные и должен храниться по правилам конкретной медицинской организации.

## 14. Медицинские ограничения

- только взрослые 18+;
- текущая версия не предназначена для беременности;
- не предназначена для неотложных состояний;
- не является автономным диагностическим устройством;
- не назначает лечение;
- `Model score` не является вероятностью диагноза;
- МКБ-10 выводится как справка;
- данные одного частично синтетического датасета не доказывают клиническую эффективность;
- перед реальным внедрением нужна внешняя и проспективная клиническая валидация, а также организационная, ИБ и регуляторная оценка.
