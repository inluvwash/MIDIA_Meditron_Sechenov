# Архитектура Meditron

Команда: **Мидия**  
Кейс: Сеченовский университет — AI-скрининг латентных дефицитных состояний по лабораторным данным.

## Основной принцип

Система не строится вокруг одного «умного» алгоритма. Каждый вычислительный слой имеет отдельную ответственность и может быть проверен независимо.

```text
Файл / TXT / ручной ввод
        │
        ▼
1. Нормализация + safety gate
        │
        ├──────────────┐
        ▼              ▼
2. Клинические правила 3. ML: 12 классов
        │              │
        └──────┬───────┘
               ▼
4. Карта неопределённости
               │
               ▼
5. Причинно-следственные связи
               │
               ▼
6. Похожие лабораторные профили
               │
               ▼
7. Опциональное локальное AI/RAG-объяснение
               │
               ▼
Врачебный интерфейс / PDF / режим разговора с пациентом
```

Карточка пациента, итоговое резюме, МКБ-10, локальная case-base и human-centered представление — **не отдельные диагностические слои**, а инфраструктурные и коммуникационные компоненты вокруг семи вычислительных слоёв.

## Изоляция личности

ФИО существует отдельно от медицинского payload.

`HealthScreening.py` передаёт в `screen()` только обезличенные данные. ФИО используется для текущей карточки и PDF, но не входит в признаки ML, JSON результата, RAG или локальную case-base.

При опциональном AI-разборе клинического текста ФИО и очевидные прямые идентификаторы удаляются до обращения к локальной Ollama.

## 1. Нормализация и safety gate

`screening/importers.py`, `screening/schema.py`, `screening/context_ai.py`

- один файл = один пациент;
- многостраничный PDF объединяется в одну редактируемую карточку;
- PDF/TXT могут предзаполнять ФИО, возраст, пол и клинический контекст;
- клинические секции разделяются на «Жалобы / симптомы», «Анамнез» и «Препараты»;
- опциональный локальный LLM может только структурировать неструктурированный клинический текст;
- неизвестные единицы не используются молча;
- технически невозможные значения блокируются;
- возраст <18 блокируется;
- беременность остаётся backend safety-gate как профиль вне области применения.

Все импортированные поля остаются редактируемыми врачом до запуска расчёта.

## 2. Детерминированный клинический слой

`screening/clinical.py`

Прозрачные правила оценивают:

- Hb и наличие анемии;
- железный обмен с учётом воспалительного контекста;
- B12 / MMA / активный B12 / гомоцистеин;
- фолаты;
- B6;
- медь;
- inflammatory pattern;
- mixed deficiency hints;
- узкий safety-check: почечная функция, гемолиз, тиреоидное направление.

Этот слой не зависит от LLM и может поддержать или оспорить ML.

## 3. ML layer

`screening/ml.py`

Random Forest классифицирует профиль по **12 классам `anemia_class`**. В модель входят возраст, пол и 35 лабораторных признаков. Жалобы, анамнез и препараты не являются ML-признаками, потому что отсутствуют в обучающем датасете.

`predict_proba` отображается как **Model score**, а не как клиническая вероятность диагноза.

## 4. Uncertainty-first layer

`screening/uncertainty.py`

Ключевой продуктовый слой:

1. показывает ведущую и альтернативную гипотезы;
2. объясняет, почему между ними остаётся неоднозначность;
3. оценивает недостающие маркеры;
4. выбирает наиболее информативное следующее измерение в рамках настроенных правил и model perturbation.

Цель — показать врачу не длинный список исследований, а **какой диагностический вопрос остаётся нерешённым и какое измерение лучше всего его проясняет**.

Сопутствующие сигналы выводятся отдельно и не трактуются как взаимоисключающие диагнозы.

## 5. Причинно-следственные связи

`screening/causal.py`

Форма представления:

```text
Что видим → Что это поддерживает → Что может объяснять
```

Свободный текст жалоб, анамнеза и лекарств участвует именно здесь. Причина показывается только при наличии соответствующего сигнала в введённом контексте.

Это **causal reasoning / explanation layer**, а не строгий causal inference и не цифровой двойник.

## 6. Похожие профили

`screening/similar.py`, `screening/casebase.py`

Поиск выполняется по:

- предоставленной reference-выборке;
- локально подтверждённым обезличенным случаям врача.

ФИО и свободный клинический текст в case-base не сохраняются. Добавление случая не переобучает Random Forest автоматически.

## 7. RAG + local LLM explanation

`screening/rag.py`

LLM получает уже рассчитанный class, клинические findings, uncertainty map, causal chains, обезличенный контекст и выбранные RAG-фрагменты.

LLM не имеет права менять:

- лабораторные значения;
- `class_code`;
- Model score;
- клинические правила;
- назначения и дозировки.

Если Ollama отсутствует, используется детерминированное объяснение. Медицинское ядро продолжает работать.

## МКБ-10

`screening/coding.py`

МКБ-10 показывается только как справка для врача. Автоматического кодирования подтверждённого диагноза нет.

## Report / human-centered layer

`screening/report.py`, `screening/communication.py`

Система не пытается симулировать эмпатию. Она уменьшает информационный шум, чтобы человеческую часть контакта оставлять врачу.

В PDF последовательно представлены:

1. карточка пациента и клинический контекст;
2. исходные лабораторные показатели;
3. итог скрининга;
4. семь вычислительных слоёв;
5. источники;
6. отдельная последняя страница для совместного объяснения результата пациенту.

В режиме разговора с пациентом технический жаргон скрывается, но остаются факты, относительный модельный рейтинг, неопределённость и упрощённая причинная схема.

## API

`api.py` использует то же ядро, что Streamlit UI. Это позволяет в дальнейшем интегрировать решение с внешними системами без переписывания медицинской логики.
